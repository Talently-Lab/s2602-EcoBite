# Deployment: Render + Neon + Vercel

This prepares a free demonstration deployment, not an always-on production SLA.
Nothing in this setup resets the database. Schema migrations run before API
startup; data imports are a separate, explicit operation.

## Target URLs

| Service | Target |
| --- | --- |
| API origin | `https://ecobite-api.onrender.com` |
| API base | `https://ecobite-api.onrender.com/api` |
| Scalar reference | `https://ecobite-api.onrender.com/docs` |
| Portal | `https://ecobite-api-portal.vercel.app` |
| Portal docs redirect | `https://ecobite-api-portal.vercel.app/docs` |

These are requested names, not reserved domains. If either provider assigns a
different hostname, use its actual URL everywhere below and in the meeting sheet.
HTTPS is provided by the hosts; no domain purchase is needed.

## 1. Prepare the release

- Link this work to the team's existing deployment issue, if one exists.
- Review and merge the deployment branch into `main` through the normal PR
  process. Do not create resources from an unreviewed branch.
- Require the existing `Backend checks` and `API Portal checks` on `main` in
  GitHub branch protection. The workflow files alone do not enforce this.
- CI uses a Prisma double: it does not validate a live database or migrations.
- No GitHub Actions job that handles PRs needs production database secrets.

## 2. Create Neon

1. Create a Free project named `ecobite`, with PostgreSQL **16**. The backup
   workflow uses a matching `pg_dump` major version.
2. Prefer AWS Oregon (`us-west-2`) to match the Render blueprint. If unavailable,
   choose compatible nearby regions on both services.
3. Keep one persistent production branch/database. Do not connect PR previews
   or local experimentation to it.
4. From Neon's connection dialog, keep the **pooled** connection URI for
   `DATABASE_URL`, and the **direct/non-pooled** URI for `DIRECT_URL`.
   Preserve the provider's SSL parameters. Both must point to the same database.
5. Store these only in a password manager and the provider secret settings.
   Never paste them into chat, issues, commits, screenshots, or terminal history.

The API uses `DATABASE_URL`. Prisma migrations prefer `DIRECT_URL`; locally it
can be omitted. The seed uses `DATABASE_URL`, not `DIRECT_URL`.

## 3. Create the Render API

In Render, choose **New > Blueprint**, connect this GitHub repository, select
`main`, and use the root `render.yaml`. There is no Render database in the
blueprint: data lives in Neon.

| Variable | Setup |
| --- | --- |
| `DATABASE_URL` | Paste the pooled Neon URI into Render's secret input. |
| `DIRECT_URL` | Paste the direct Neon URI into Render's secret input. |
| `JWT_SECRET` | Generated by the blueprint; keep it stable between deploys. |
| `CORS_ORIGINS` | Defaults to `https://ecobite-api-portal.vercel.app`. Add the actual customer frontend origin when available, comma-separated. |
| `TRUST_PROXY_HOPS` | Blueprint sets `1` for the controlled Render ingress; local default is `0`. |
| `NODE_ENV` / `NODE_VERSION` | Blueprint supplies `production` / Node `22`. |
| `PORT` | Supplied by Render; do not replace it with the local port. |

The build runs from the monorepo root, keeps the single frozen lockfile, and
builds only `backend`. Dev dependencies are intentionally installed because the
Prisma CLI is needed at startup on the Free plan.

Startup runs `prisma migrate deploy && node dist/index.js` through package
scripts. It only applies pending committed migrations; it never calls
`migrate dev`, `migrate reset`, `db push`, or the seed. A migration/database
failure blocks listening. Future migrations must be backward-compatible because
the old process may still serve requests during a deploy.

`autoDeployTrigger: checksPass` waits for GitHub checks on `main`. Verify this
setting in Render after importing the blueprint; do not replace it with
unconditional commit-triggered deploys. The initial deployment should use a
commit whose existing CI checks have succeeded.

The `/api` health check is process liveness only. The deployment smoke test also
queries `/api/restaurants` to exercise the real database.

Render Free sleeps when idle and may restart; allow about a minute for a cold
start. This does not delete Neon data. Do not store application data or backups
on Render's ephemeral filesystem.

Before public use, confirm the real proxy topology and rate-limit isolation
from two networks. The implementation trusts exactly one nearest hop, not
arbitrary `X-Forwarded-For` values. If clients share a rate-limit bucket, inspect
the topology rather than blindly increasing trust. Keep one replica while the
rate-limit store is in memory.

## 4. Load reference and analyst data

Order: **schema migrations -> reference seed -> approved analyst import ->
endpoint verification**. Do not import a local database wholesale or run a reset.

After Render's first successful startup, open a separate PowerShell terminal at
the repository root. These prompts keep the connection URI out of shell history:

```powershell
$secureUrl = Read-Host 'Neon pooled DATABASE_URL' -AsSecureString
$env:DATABASE_URL = [System.Net.NetworkCredential]::new('', $secureUrl).Password
$env:DOTENV_CONFIG_PATH = [System.IO.Path]::GetFullPath('backend/.env.example')
pnpm --filter backend prisma:seed
if ($LASTEXITCODE -ne 0) { throw 'Seed failed; stop before importing analyst data.' }
```

Close that terminal afterward to discard its environment. The committed seed
upserts **48 zones and 8 packaging types**. It is not a restaurant/product import.

The analyst's S3 CSVs and import mapping are now available; follow the
[backend import instructions](../backend/README.md#importación-del-dataset-s3).
The approved mapping excludes the 94 simulated courier accounts, not orders;
all 800 orders remain. Run the default offline validation first, then test on an
isolated local database before approving an explicit `--apply` against Neon.
Pending enum migrations and the reference seed must be applied first.
Do not invent rows or run arbitrary supplied SQL against production. Take a
backup before an approved production import. Restaurants appear publicly only
when active and eco-friendly.

## 5. Create the Vercel portal

1. Import this same repository as a new Next.js project.
2. Set project name **`ecobite-api-portal`**, Root Directory **`api-portal`**,
   Node **22.x**, and Production Branch **`main`**.
3. Allow source files outside the Root Directory so Vercel can use the workspace
   and root lockfile. Keep the committed `api-portal/vercel.json` commands.
4. Set `API_DOCS_URL=https://ecobite-api.onrender.com/docs` for Production
   (replace the hostname if Render assigned another one).
5. Preview deployments should use a separately chosen docs target, not receive
   database credentials. Set `API_DOCS_URL` there too if previews are enabled.

The portal needs **no** database URL or API JWT secret. Production `/docs` fails
explicitly if `API_DOCS_URL` is missing, rather than sending visitors to localhost.
Scalar uses a relative `/api` server, so Try It calls the host serving the docs.

Vercel's Git integration handles deployments. Require CI before merging to
`main`; do not assume Vercel's build automatically waits for unrelated Actions
checks. The backend's explicit Render checks gate is separate.

## 6. Enable independent encrypted backups

Neon persistence is not a promise of indefinite storage or a backup strategy.
Free-plan quotas, account suspension/deletion, and limited recovery history still
apply. Check current plan limits rather than relying on a particular restore window.

The opt-in `Database Backup` workflow makes a daily custom-format Postgres dump
at 06:30 UTC (03:30 in Buenos Aires), encrypts it with GPG, and uploads **only**
the encrypted archive. No credentials or raw dumps are uploaded. It can also run
manually. GitHub may delay schedules or disable them after repository inactivity.
Each run checks the archive's table of contents and verifies an encryption/
decryption round trip before upload. This does not replace an isolated database
restore drill.

1. Create a GitHub environment named `production-backup`, restricted to `main`.
2. Add environment secret `DATABASE_BACKUP_URL`: the **direct** Neon URI.
   Prefer a dedicated read-only backup role with access to the application
   tables/sequences, including future tables; do not change application roles.
3. Add environment secret `BACKUP_PASSPHRASE`: a separate random secret of at
   least 32 characters. Save a copy in a password manager: losing it makes the
   archives unrecoverable. Do not reuse `JWT_SECRET`.
4. Set repository variable `ENABLE_DATABASE_BACKUPS` to `true`.
5. In Actions, run `Database Backup` on `main`, verify success, and download the
   encrypted artifact. Check your Actions failure-notification settings.

Artifacts expire after **14 days**. Before the meeting and periodically afterward,
download one to a secure location outside the repository and keep a second
independent copy. Stay within GitHub Actions/storage free quotas; do not enable
paid overages to make this setup work.

To decrypt a downloaded archive, use GPG's interactive passphrase prompt:

```powershell
gpg --output C:\SecureBackups\ecobite.dump --decrypt C:\SecureBackups\ecobite.dump.gpg
```

Keep decrypted dumps private: they contain account data and password hashes.
Inspect with `pg_restore --list`, then do a restore drill with PostgreSQL 16 tools
against a **new isolated empty database**, never the live one. Use
`--no-owner --no-acl --single-transaction`; verify reference row counts and API
behavior there. Restore into live data requires a separate approved recovery
procedure. Do not use `--clean`, drop tables, or reset to demonstrate a restore.

If backups fail, check the direct URL, backup-role grants, server major version,
and Actions availability. Check the last successful artifact's timestamp before
claiming the database is backed up.

## 7. Acceptance and meeting

Follow [the meeting sheet](demo-api.md). A deploy is not accepted just because
the homepage responds: verify real restaurant data, login/profile, docs target,
portal redirect, and a downloadable backup. Recheck a known row after an API
redeploy to confirm that the same Neon database is still attached.

No cloud resources, live credentials, analyst import, backups, or endpoint
requests are executed merely by committing these files. Provider-side setup and
live verification remain explicit steps.
